The problem

Companies were forecast to spend $723 billion on public cloud in 2025, and nearly a third of it is wasted. When something breaks, the answer is spread across a dozen consoles, runbooks and people’s heads. AI can answer fast, but no engineer will put an answer they can’t check on call.

Scattered

Cost, security and performance data live in separate tools, each with its own console.

Untrusted

A confident paragraph from a model isn’t evidence. Without sources, it can’t be acted on.

Manual

Fixes are still written by hand in Python, Bash and Terraform, one incident at a time.

The data to fix all of this already exists. Nothing connects it, checks it and acts on it safely.

Who it’s for

A staff-level SRE who owns production reliability and writes the runbooks today. Their test is simple: would I put this on call?

Sketches

Ideas from stakeholders became HTML sketches people could click, long before they reached the prototype. There are 24 of them, from the knowledge base to what happens when the model goes down.

Ask

Type a question and the answer comes back as interface: numbers, tables and cards built for that question, each one citing its source. Reports run in two passes. The first finds the facts and the second writes them up, so the writing can’t claim more than the data shows.

Generative UI

The model answers in OpenUI Lang, a small language for interface. The app parses it as it streams and renders components from Escher’s library, so an answer can be a table, a chart or a calculator instead of a paragraph.

Components

The OpenUI base set, plus thirteen of Escher’s own. The model can only use what the library defines, and every recipe must parse before it renders.

Choosing the chart

The first version picked a chart from the shape of the data, which produced charts where every bar was 1. Now the form follows the reader’s question, and charts that carry no information are blocked in code.

Escher’s own bar charts

Band-scale geometry, height that follows the data, and emphasis only where it’s asked for.

Figures and calculators

The model can draw an explanatory figure or build a small calculator. Both are sanitised before they render.

Guards in code

No chart of zeros, no invented capitals in legends, and a section heading always stays with its figure.

Plan and execute

A fix arrives as a plan with its blast radius and risk shown up front. You read the change like a diff, approve it, and watch each step run, with a record of why every step happened.

Design mode

Operators write playbooks by talking them through instead of scripting them. Imported runbooks become playbooks too, and each one keeps its success rate and evidence.

Agents

Agents start as drafts, run in shadow until their results earn trust, then go live one playbook at a time. One switch drops every agent back to propose-only.

Strictest rule wins

Three settings decide what an agent may do: its own mode, the grant on each playbook, and one org-wide break-glass lever. The strictest of the three always wins.

One token file builds CSS variables, a Tailwind theme and typed tokens, and every app reads from it. Change a colour once and every app picks it up.

Architecture

Three layers. The browser composes each turn and renders the answer. A thin API layer talks to models, the estate database and AWS. Every claim in an answer traces back to a row or a command output.

One turn

A question becomes a short loop of tool calls, then an answer built from what the tools returned.

  1. 1ComposeThe browser builds the prompt and the list of tools the model may call.
  2. 2GatherThe model queries the estate, searches it and runs read-only AWS commands, up to three rounds.
  3. 3AnswerThe reply streams back as OpenUI Lang and renders as cards, tables and charts.
  4. 4Second passA report or plan opens as its own pass, so the write-up only uses facts already found.
  5. 5RecordFindings are created from tool results, never from the model’s prose.

Safety in code, not in the prompt

A role named read-only can still carry write permissions, so the checks live in the API, not in IAM or the system prompt.

Reads

  • Commands run as an argument list with no shell, so ;, pipes and $() mean nothing.
  • Only allowlisted read verbs run.
  • The profile must exist on the machine, or the call is refused.
  • Every call has a timeout and an output cap.

Writes

  • The model can only propose a change. Its tool loop has no path to the write endpoint.
  • Each step runs only after a person clicks it.
  • The first step records the current state, so rollback restores it.
  • Model IDs are allowlisted, and the deploy sits behind a signed password cookie.

Data model

The estate is thirteen Postgres tables. resources holds current state. Everything around it keeps the history: what changed, what each resource looked like before a scan, how resources connect, and an embedding of each one for search.

All or nothing

A scan is classified in one transaction, so a half-finished scan can never read as a complete one.

Diff by hash

Each resource has a content hash. Unchanged resources are left alone, and a deleted resource that comes back counts as new.

Encrypted

Sensitive payloads use AES-256-GCM with a fresh IV each time, so matching resources never produce matching ciphertext.

Scanning

Every resource type in every region is its own read-only call. They all go into one queue that runs twelve at a time, so the limit is AWS throttling, not the order of the work.

A call that fails is recorded and retried with backoff. A scan that couldn’t look never reports a clean estate.

Model layer

Every route speaks Anthropic’s Messages API, because prompt caching only exists there. Claude models go straight to Anthropic. Other models go through OpenRouter’s Anthropic-format endpoint, so the request and the stream parser stay the same.

Only model IDs on an allowlist reach a provider. If a model has no key configured, the user gets a sentence explaining why, not a dead stream.

Token optimisation

Every request carried about 11,000 tokens before the conversation even started: a 9,000-token system prompt and 2,200 tokens of tool schemas. A report turn made five to eight model calls, and each one re-read the whole conversation.

I measured it first, then cut it without changing a single answer.

Three tiers

Every idea was sorted by how much it could change an answer. Only the first tier ships without an evaluation.

Execution

The model can propose a change but has no way to run one. Each step runs only after a person confirms it. The first step records the current state, each step is re-read after it runs, and a step can stop the run or ask before going on.

Evaluation

Answers are graded by six plain functions, not by another model. They check that every number came from a tool result, that knowledge answers cite a source, and that the interface code parses. They run in CI with no API key.

Outcome

Tessell uses the prototype to demo Escher to potential customers and investors. Its frontend code moves straight into the Tauri app, so the prototype works as a spec as well as a demo.

What I learned

A bigger role

I started as a product designer making a prototype. Now I build the frontend of the desktop app as well.

A different process

Design happens in working code instead of static mockups. The sketch, the prototype and the shipped frontend are the same material.

A faster pace

Ideas go from sketch to something people can click in days, not weeks.
