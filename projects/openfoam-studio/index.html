Problem

OpenFOAM is one of the most capable CFD solvers there is, and one of the hardest to use. An engineer can describe a case in one sentence. OpenFOAM needs it as a folder of plain text files with no schema, and the files have to agree with each other.

I first hit this during my bachelor’s thesis, then saw students in a CFD course get stuck the same way. I work in product design now, and this project is my way back into that field.

The hard part is the tooling, not the physics.

Who it’s for

Engineers who understand fluid dynamics but don’t want to become OpenFOAM configuration specialists.

Primary

Mechanical and aerospace engineers

They know the physics. They want a case running in minutes, with files they can still check.

Secondary

Researchers

Quick sweeps across Reynolds number, geometry or model, without boilerplate case files for each run.

Not for

Meshing and CAD

GUI mesh generation and CAD import are a different problem, and out of scope.

The model

Every simulation goes through five steps. If a run fails, review sends it back with a fix.

Principles

Inspectable

The AI writes dictionaries, not results. Every file is open in the editor before it runs.

Real solver

No surrogate model and no predicted flow. blockMesh, foamRun and foamToVTK run in a container.

Correct, not just running

A case that converges to the wrong answer is worse than one that fails loudly.

Local

Everything runs on your machine, and the agent never gets a raw shell.

Describe

Type a case in plain English. The agent writes the case files in dependency order, so the patch names in the mesh match every boundary condition. Follow-up messages change only the files that need it.

Inspect

The layout borrows from code editors: file tree on the left, editor in the middle, chat on the right. Files open as the agent writes them, and a Parameters tab turns the main values into fields you can edit without touching syntax.

Results

Solved cases open in a 3D viewer inside the app, modelled on ParaView and ANSYS CFD-Post. A result is a pipeline: the mesh coloured by any field, then slices, clips, iso-surfaces, streamlines and vector glyphs, each with its own settings, played over every saved time.

Setup

Docker and a model are the two things that stop people on day one. A health check runs on first launch, checks Docker, the OpenFOAM image and the model login, and repairs what it can. Bring your own key or point it at a local model through Ollama.

System design

Most of the work is here: what runs where, what the model can and can’t touch, and how a failed run gets back on track.

Architecture

Electron starts a local Node server, and the React interface talks to it over REST, with live updates as server-sent events. All the real work lives in core/, plain Node with no Electron in it, so the whole pipeline runs and is tested without a window.

Headless core

No Electron import is allowed in core/. Every module can be run and tested from a terminal.

Thin shell

Electron only starts the server, waits up to 30 seconds for it to answer, then loads the interface.

One port

The server serves the built interface and the API from localhost:3456, so the browser and the app see the same thing.

Agent loop

Generation is a tool-calling loop, not one big prompt. The model gets eight tools and works until it calls finish or reaches 16 steps. Its instructions tell it to save the last steps for blockMesh, checkMesh and a short solver run, so it tests a case before calling it done.

Every step streamed

Knowledge

The agent looks things up instead of relying on memory. A keyword index covers 48 pages of the OpenFOAM 13 manual and 18 wiki pages, split at headings. Search returns the source path, so the agent can read the whole page and cite it.

Sandbox

Every solver command runs in a fresh container with only the case folder mounted, and the container is removed when the command ends. Commands are checked against an allowlist in code, not in the prompt, and every argument is shell-escaped.

  • blockMesh
  • checkMesh
  • setFields
  • foamRun
  • foamToVTK
  • icoFoam
  • simpleFoam
  • pimpleFoam

The whole allowlist. Anything else is refused before a container exists.

$

Fresh each time

No container outlives its command, so no state leaks between runs.

Windows paths

The usual src:dst bind broke on the colon in C:\, so mounts use an explicit mount object.

Honest exit codes

The stream can end before Docker records the exit code, so the runner polls until it’s final instead of guessing.

Recovery

Recovery has two tiers. Known failures are matched by pattern and fixed by set rules, with no model call. Anything else goes to an LLM reviewer, which returns a corrected file or says it can’t identify the problem instead of guessing.

Storage and streams

There’s no database. Each project is a folder, with append-only logs for runs and commands. Generation, runs and repairs all reach the interface as server-sent events.

Event payloads are simplified here.

Plain files

An OpenFOAM case is already plain files, so the same folder opens in ParaView or a terminal. Nothing is locked inside the app.

Append-only

Runs and commands are added as new lines and never rewritten, so a crash can’t corrupt the history.

One stream per job

Closing the request cancels the job, and on a run that kills the container.

Results pipeline

After a run, foamToVTK converts every time step inside the container. The server builds a list of steps and patches, and the interface fetches each step when it’s needed. vtk.js has no reader for this format, so I wrote one.

Own parser

vtk.js has no reader for legacy unstructured VTK files, so the interface parses them itself.

Cached steps

Parsed steps are kept in memory, so scrubbing through time never reads from disk twice.

One engine

All vtk.js code sits behind one class. When WebGL drops its context, the viewer recovers instead of going blank.

How I worked

I built it with AI coding agents, in stages. No layer started until the layer below it passed its tests. A markdown wiki of OpenFOAM knowledge and an agent change log kept every session grounded.

Outcome

Version 1.0.2 is out on GitHub for macOS and Windows, under the MIT licence. It’s validated on the lid-driven cavity and works best on incompressible laminar cases for now. Next, I’m sharing it with a professor for feedback.

What I learned

End to end

Every project before this was product design only. This is the first one I took from problem to shipped software: design, code, tests, packaging and release.

Systems, not screens

Most decisions were about where safety lives: in code, not the prompt; in rules for known errors, with the model only for the rest.

Correct over working

Using a benchmark as the pass gate changed what “done” meant.
